## Decisiones del implementador (para el auditor)

- **CLI fija en vez de `claude-code-action@v1`** (ver ajuste en el brief §4): la Action está pensada para escribir; acá se busca garantizar por argumento que no haya escritura ni token de GitHub. La Action vuelve con PR 3 si se aprueba la escritura.
- **Registro en check-run** (no etiqueta ni comentario): durable, legible por API (las métricas quedan en su `output`, que los agentes leen aunque el proxy no deje bajar logs), sin tocar el PR. Costo: `checks: write`, que también permitiría publicar otros checks con el token del run; mitigado porque ningún paso con ese token ejecuta código del PR ni a Claude.
- La cuenta de Fer la usan también los agentes: el disparo por comentario exige `@claude` como primera línea y rechaza el pie de Claude Code. En solo lectura un falso disparo cuesta cuota, no escrituras.

## Límites declarados

- El secret no se puede verificar por API desde esta sesión (proxy: 403 en `actions/secrets`); el HANDOFF dice que Fer lo cargó. Si falta, el paso de Claude falla con "falta CLAUDE_CODE_OAUTH_TOKEN" y la anotación lo dice.
- Prompt injection: el contenido del PR llega a Claude como dato delimitado; sin escritura, procesos ni red, lo peor es una respuesta engañosa en el log. Los tokens se tapan antes de publicar (además de la máscara de secretos de GitHub).
